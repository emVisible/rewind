# Rewind 目录结构优化方案

> 版本:v1.0(2026-10-06)
> 前提:本轮**只拟方案不动文件**。执行时按阶段走,每阶段跑全套闸,任一阶段闸红就回滚该阶段。
> 口径:根级兄弟布局(`core/ shell/ app/ presets/ …`,无根 `Cargo.toml`)与 ALH Pro 必须在仓库外,是 load-bearing 约束,本方案不碰。

## 二、要做的(按性价比排序)

### A 组 · 纯清理,低风险,建议先做

**A1 删 `app/ui/dev_assets/` —— 这是本轮唯一的"脏在发布路径里"的问题**
5 张调试残图(`test_src_@1s_crt1995.png` 等,316 KB),**已被 git 跟踪**,而 `tauri.conf.json` 的 `frontendDist: "ui"` 意味着整个 `app/ui/` 进安装包;Web 版静态服务同样能取到 `/dev_assets/…`。它们不是"乱",是"把 10 月 4 日的调试现场发给了用户"。
配套契约(进 `release_check`):`app/ui/` 下只允许 `index.html app.js style.css shim.js i18n.js favicon.ico img/ gallery/`,出现别的条目就红 —— 白名单而不是黑名单,否则下次长出来的还是看不见。
验证:删后 `GET /dev_assets/out_default.png` 必须 404;契约反向注入(造一个 `app/ui/zzz/`)必须判红。

**A2 `assets/reference.png` → `assets/reference/reference.png` + `CREDITS.md`**
和 `sample/` 同形(素材 + 来源声明)。真正的目的不只是整齐:`reference.png` 是第三方《金坷垃》截图,而 44 张画廊对比图和 README 配图全都由它烘出来 —— 现在许可状态只存在于对话记录里,放进 `CREDITS.md` 才成为仓库事实。这一步不解决许可,只是让它无法被忽略。
改动点 4 处:`preset_gallery.sh:12`、`regression.sh:170,177`、`release_check.sh:187`、`README.md:26,74`。

**A3 README 界面段落与实况对齐**
`README.md:70` 还写着左栏含"年代轴 + 四组常用物理量",而上一轮已把年代轴/偏色移进高级参数、一级组收成 3 组。文档比代码旧,是开源仓库最伤信任的那种旧。

**A4 给被取代的规划文档盖一个"已被取代"戳**
`docs/product/界面与产品完善规划.md`(2026-10-04,v2 界面重设计,自称"定案")已被 `预设体系与界面体验规划.md` 事实上接管(M6 各项已落地,后者带 D1–D26 与实测数字)。不删(它是决策记录),只在头部加一行指向现行文档 —— 新人读到两份"定案"会不知道信哪个。

### B 组 · 有真实收益,但要动配置,建议第二批

**B1 `scripts/` 去掉里程碑前缀,但**不**分子目录**
`m4_axis_check.sh`、`m4_sheets.sh` 的 `m4_` 是已完成里程碑的编号,对新读者纯属噪音(它不告诉你这脚本干什么)。改成 `axis_check.sh`、`compare_sheets.sh`。
**明确不做 `scripts/gate/` + `scripts/bake/` 分层**:12 个文件还没到需要分层的量,而代价是各脚本里 `ROOT=$(dirname $0)/..` 全要变 `../..`、CI 8 处、`release_check` 自述路径、README —— 纯风险换不到可读性。等超过 20 个脚本再说。

**B2 `.work/` 治理:一个入口 + 一张清单**
478 MB 散在 6 个自造名字里,没有清理入口,也没有"哪些能删、删了怎么重建"的说明。做三件小事:
1. `scripts/clean_work.sh`:按子目录列体积,`--yes` 才删;默认只报告。
2. 各闸输出目录统一成 `.work/gate/<闸名>`(现在 `geo/axis/conc/regression/release` 各叫各的)。
3. `.work/samples/`(291 MB 定标样片)加一份 `HOWTO.md` 写清重建命令 —— 它可再生,但今天只有我知道怎么再生。
这条的收益是操作摩擦,不是美观。

**B3 共享 cargo target —— 先量再决定,不许凭感觉改**
`core/target` 833 MB + `shell/target` 213 MB,依赖大量重叠(serde/clap/tauri 系)。用 `.cargo/config.toml` 指到 `.work/target/` 可能既省磁盘又加快增量编译。
但这是**未测量的假设**:共享 target 会让 CI 缓存 key 变、可能引入 feature 统一化导致的重编。执行前先在本地各跑一次干净构建计时 + 量体积,数字支持才做;不支持就把这条划掉并在本文档留一行结论。

## 三、明确不动(附理由,免得下一轮重新怀疑)

| 项 | 不动的理由 |
|---|---|
| `presets/` 挪进 `assets/` 或 `core/` | 根级兄弟关系是 load-bearing:`CARGO_MANIFEST_DIR/../presets`(测试)、`assets.rs` 解析、`serve.rs`、CI 拷贝、桌面 `bundle.resources` 五处各自指向它。收益只是"根目录少一个",风险是运行时找不到预设 |
| `app/engines/`、`app/presets/` 搬去 `.work/` | 它们是 CI 造的 Tauri 打包暂存,`bundle.resources` 按 `tauri.conf.json` 所在目录相对解析,跨目录引用在本机无法验证(无 GUI 依赖)。已 gitignore。要做的是**加断言**(不入库 + CI 步骤存在),即任务 #22,而不是搬 |
| `fixtures/` 与 `assets/sample/` 合并 | 语义不同:前者是测试输入(含故意奇数尺寸/坏文件),后者随产品分发、有许可要求。合并会让"哪些文件进安装包"变模糊 |
| `docs/重构文档.md` 改名或下沉 | 它是工程台账,README 第一句就指向它;24 处引用换零收益 |
| `vendor/ntsc-rs` 改回 git 依赖 | 当初 vendor 的原因是它带 openfx 子模块,那条约束没消失 |
| `webui.sh` 挪进 `scripts/` | 它是用户入口,放在根目录是对的(和 README 平级才找得到) |
| `core/src/ffgraph.rs` 1444 行拆分 | 那是代码组织不是目录结构,且现在动它会和进行中的功能改动撞车;单列议题 |

## 五、我替你定的几件事

1. **`app/ui/dev_assets/` 直接删,不归档** —— 它是调试残图,不是历史;真要历史,git 里有。

3. **`reference.png` 的许可问题这轮仍然只暴露不解决** —— 换基准图会重烘 44 张对比图和 README 配图,而你正在看这些卡片的观感;先把它写进 `CREDITS.md` 变成仓库事实,等你确认观感定稿再换图重烘。
4. **共享 target 不凭感觉改** —— 先量,量不过就划掉。
5. **README 过期段落随第一批一起修** —— 文档与实况不一致,按缺陷处理,不按"以后再说"处理。

### 阶段 5 的实测数字(共享 target 否决依据)

| 方案 | 干净构建耗时 | 体积 |
|---|---|---|
| A 分离 target | core 15s + shell 4s = **19s** | 131M + 39M = **169M** |
| B 共享 `.work/target` | core 13s + shell 4s = **17s** | **149M** |

省 2 s / 20 MB,代价是 12 处 `core/target/release/...` 脚本引用、CI 缓存 key、可执行文件不再从 crate 目录可寻。**不划算,否决。**
但测出了真病因:之前看到的 833M + 213M 不是"结构问题",是**从来没 `cargo clean` 过**;于是把它变成一条命令 `clean_work.sh --targets`。
